# Scout SOP - AI Coding Execution Standard

**Version**: v1.0  
**Date**: 2026-05-28  
**Applies to**: Scout coding agents, human operators, reviewer agents, and parallel sub-agents  
**Primary input**: `PRD_0528.md`  

---

## 1. Purpose

This SOP defines how to develop Scout with AI coding agents without letting the project drift into chaotic "prompt-and-pray" development. It translates vibe coding, Claude Code, and Codex best practices into a concrete operating process for this repo.

The goal is not to make agents write as much code as possible. The goal is to make every agent change small, reviewable, logged, testable, reversible, and aligned with the competition scoring criteria.

---

## 2. Operating Principles

| Principle | Rule |
|---|---|
| Spec first | Read `PRD_0528.md` before coding. If a task conflicts with the PRD, stop and ask. |
| Small slices | One agent task should produce one reviewable slice, not a broad rewrite. |
| Context over vibes | Give agents exact files, contracts, constraints, and acceptance criteria. |
| Verify hard | Trust tests, logs, builds, traces, screenshots, and diffs over verbal confidence. |
| Git is the safety rail | Branch, diff, commit, review, merge. Do not let AI bypass version control. |
| Logs are product evidence | Run Event logs and Run Summary are part of the deliverable, not optional debug output. |
| Mock-first | The main demo must run without external network collection. Web features are additive. |
| Human owns acceptance | AI may implement, but humans or a review agent must accept P0 behavior. |

## 4. Standard AI Coding Loop

Use this loop for every non-trivial change:

```text
Explore -> Plan -> Implement -> Verify -> Review -> Commit -> Log
```

### 4.1 Explore

The agent must identify:

- Relevant PRD sections.
- Files to read.
- Files likely to change.
- Contracts that must not change.
- Risks and unknowns.

No code edits during Explore unless the task is explicitly a small documentation edit.

### 4.2 Plan

The plan must include:

- Goal.
- Write scope.
- Read-only scope.
- Acceptance criteria.
- Verification commands.
- Branch name.
- Rollback plan.

For P0 features, the agent must mention the matching PRD requirement ID when available.

### 4.3 Implement

Implementation rules:

- Keep diffs small.
- Do not change public Schema/API contracts unless the task is a Schema/API task.
- Do not mix backend, frontend, data, docs, and tests in one giant task unless it is a tiny vertical slice.
- Prefer boring, explicit code over clever abstractions.
- Add comments only where they reduce future confusion.

### 4.4 Verify

Minimum verification depends on the change:

| Change type | Required verification |
|---|---|
| Backend model/API | Import check, Pydantic validation, API smoke path |
| LangGraph/Agent | Run mock task, broken case, Run Event output |
| Frontend | Build/typecheck if available, manual page path, no broken layout |
| Data pack | Schema validation, source count, broken case still intentional |
| Docs only | Links/paths/commands consistent with repo |

If dependencies are not installed yet, document the blocked command and why it could not run.

### 4.5 Review

Review must check:

- Does this satisfy the PRD requirement?
- Is the diff smaller than necessary?
- Did it introduce dependencies?
- Did it log success/failure where required?
- Did it protect secrets and sensitive data?
- Does it preserve demo stability?

### 4.6 Commit

Commit only after verification. Use clear commit messages:

```text
feat: add run event logging
fix: route reviewer missing-source issue to researcher
docs: add demo smoke test SOP
data: add ai agent broken pricing source case
```

### 4.7 Log

Update `docs/ai_coding_log.md` after meaningful changes:

```markdown
## 2026-05-28 - <short task name>

- Agent/tool:
- Branch:
- Goal:
- Files changed:
- Prompt summary:
- Decisions:
- Verification:
- Known risks:
```

## 5. Branch and Git Policy

### 5.1 Branch Naming

| Work type | Branch format | Example |
|---|---|---|
| Feature | `feature/<scope>` | `feature/langgraph-orchestrator` |
| Bug fix | `fix/<scope>` | `fix/reviewer-routing` |
| Docs | `docs/<scope>` | `docs/run-logging` |
| Data | `data/<scope>` | `data/ai-agent-pack` |
| Chore | `chore/<scope>` | `chore/backend-deps` |

### 5.2 Must Open a Branch

Open a branch for:

- Any runtime code.
- Schema/API changes.
- LangGraph DAG changes.
- Agent prompt or Reviewer rule changes.
- Dependency or build changes.
- New data packs.
- Large documentation restructuring.

### 5.3 May Push Directly to Main

Direct `main` edits are allowed only for:

- Typo fixes.
- Small Markdown clarifications under roughly 30 changed lines.
- Non-contract documentation that does not affect implementation.

Never direct-push:

- `.env`
- API keys
- raw private data
- generated runtime artifacts unless explicitly required
- broad refactors

### 5.4 Merge Gate

Before merging to `main`:

1. Show changed files.
2. Show verification commands and results.
3. Confirm no secrets or raw private data.
4. If Agent/Reviewer changed, rerun the broken case.
5. If frontend changed, run or manually inspect the main demo path.
6. Record the latest successful `task_id`, `run_id`, branch, and commit in Run Summary or the PR note.

## 6. Logging SOP

Scout has two kinds of logs:

1. **Development logs**: explain how the repo changed.
2. **Runtime logs**: explain how a Scout analysis run behaved.

### 6.1 Development Log

File: `docs/ai_coding_log.md`

Write after:

- A P0 feature lands.
- A major prompt changes.
- A schema changes.
- A failed attempt leads to a design change.
- A sub-agent result is merged or rejected.

Do not write secrets, full `.env` values, or private source content.

### 6.2 Runtime Event Log

Files/locations:

- SQLite table: `run_events`
- JSONL mirror: `runtime/logs/{task_id}.jsonl`
- Summary: `runtime/runs/{task_id}/summary.md`

Every run must record:

- `task_id`
- `run_id`
- `git_branch`
- `git_commit`
- `data_pack`
- `schema_pack`
- `langsmith_trace` or local trace id
- fallback usage
- reviewer issues
- final report artifact path

### 6.3 Required Runtime Events

| Event | Required when |
|---|---|
| `TASK_CREATED` | Task is created |
| `RUN_STARTED` | Run begins |
| `NODE_STARTED` | Agent node begins |
| `NODE_SUCCEEDED` | Agent node succeeds |
| `NODE_FAILED` | Agent node fails |
| `RETRY_SCHEDULED` | Retry is queued |
| `FALLBACK_USED` | Mock/local fallback is used |
| `ARTIFACT_SAVED` | Source/Evidence/Claim/Report saved |
| `REVIEW_FAILED` | Reviewer blocks output |
| `REVIEW_FIXED` | Issue is fixed |
| `REVIEW_APPROVED` | Reviewer passes |
| `CHECKPOINT_CREATED` | Checkpoint saved |
| `RESUMED_FROM_CHECKPOINT` | Run resumes |
| `RUN_COMPLETED` | Run succeeds |
| `RUN_FAILED` | Run fails |

### 6.4 Logging Redaction

Before writing logs:

- Remove API keys.
- Remove `.env` values.
- Mask emails and phone numbers.
- Do not store raw private interview text.
- Store source IDs and excerpts only when public or authorized.

## 7. Failure, Offline, and Rollback SOP

### 7.1 External Dependency Failure

| Failure | Required behavior |
|---|---|
| LangSmith unavailable | Continue with local Trace Mirror and log `FALLBACK_USED` |
| LLM unavailable | Retry twice, then use Mock LLM or mark run failed with reason |
| Web source unavailable | Use Mock Pack, mark source as failed, continue demo |
| Package install unavailable | Stop, document command and network failure, do not invent dependencies |

### 7.2 Runtime Rollback

Use runtime rollback when the code is fine but a run failed:

- Resume from LangGraph checkpoint.
- Restore previous report artifact.
- Mark Run Summary with fallback or failure reason.

### 7.3 Code Rollback

Use code rollback when the implementation is wrong:

- Prefer a new fix commit.
- Use `git revert` for committed changes when needed.
- Do not use destructive `git reset --hard` unless explicitly approved.

## 8. Sub-Agent Parallel Development SOP

Use sub-agents only when work can be split by ownership and does not require shared mutable context.

### 8.1 When to Use Sub-Agents

Use sub-agents for:

- Data pack preparation.
- Frontend page implementation after API contracts freeze.
- Reviewer rule tests.
- Documentation and demo script drafting.
- Read-only architecture or codebase audits.
- Smoke test execution while implementation continues.

Do not use sub-agents when:

- Schema/API contracts are unstable.
- The same files would be edited by multiple agents.
- A bug is blocking the immediate next local step.
- The task requires nuanced product judgment from the main owner.

### 8.2 Standard Sub-Agent Brief

Every sub-agent prompt must include:

```text
Goal:
Context files:
Allowed write paths:
Read-only paths:
Do not touch:
Acceptance criteria:
Verification commands:
Expected final report:
```

### 8.3 Recommended Ownership Split

| Agent | Owns | Must not edit |
|---|---|---|
| Backend Agent | `backend/app/agents`, `backend/app/core`, backend tests | Frontend pages |
| Frontend Agent | `frontend/src/pages`, `frontend/src/components` | Backend Schema |
| Data Agent | `data/packs`, source normalization notes | Runtime code |
| Docs Agent | `docs`, README, demo script | Runtime code |
| QA Agent | tests, smoke reports, validation logs | Product logic without approval |

### 8.4 Merge Order

1. Schema/API.
2. Backend orchestration and storage.
3. Frontend pages.
4. Data packs.
5. Docs and demo script.
6. Smoke test fixes.

## 9. Claude Code Practices Adapted for Scout

Use these if the project is developed with Claude Code:

- Put stable project instructions in `CLAUDE.md`.
- Keep subagents focused: one responsibility, clear tools, clear output.
- Use hooks for guardrails where practical, especially blocking destructive commands or checking changed files.
- Use project memory for architecture, commands, and off-limits files, not for temporary TODOs.
- Use subagents to preserve context, but account for latency and merge overhead.
- Version-control project subagents if created.

Recommended Claude Code hooks for Scout:

| Hook idea | Purpose |
|---|---|
| PreToolUse block `.env` reads | Prevent accidental secret exposure |
| PreToolUse warn destructive git/shell commands | Prevent unsafe rollback |
| PostToolUse log file writes | Help maintain AI coding log |
| SubagentStop require changed-file summary | Make parallel work mergeable |

## 13. Smoke Test SOP

Run this before any Demo Review:

1. Start backend.
2. Start frontend.
3. Create task with `data/packs/ai_agent`.
4. Run analysis.
5. Confirm DAG shows Researcher -> Analyst -> Writer -> Reviewer.
6. Confirm Run Event JSONL exists.
7. Confirm Run Summary exists.
8. Confirm broken case triggers Reviewer failure.
9. Confirm checkpoint resume fixes or routes the issue.
10. Confirm report has at least 8 key Claims.
11. Confirm at least 90% of key Claims have Evidence.
12. Confirm LangSmith Trace or local Trace Mirror is visible.
13. Confirm no `.env`, key, private data, or runtime junk is staged.

Record result in:

```text
runtime/runs/{task_id}/summary.md
```

## 14. Stop and Ask Rules

The agent must stop and ask before:

- Changing PRD scope.
- Changing core Schema in a breaking way.
- Adding a major dependency.
- Removing logging, tracing, Reviewer, or checkpoint behavior.
- Touching `.env` or secret-bearing files.
- Using destructive Git commands.
- Replacing Mock-first strategy with Web-first strategy.
- Editing the same files assigned to another active sub-agent.

## 15. Source Basis

This SOP is based on:

- Vibe coding workflow guidance: small scopes, accurate context, hard verification, Git review, and normal repo workflow.
- Claude Code documentation patterns: project memory, hooks, subagents, separate context windows, focused subagent responsibilities, and version-controlled project agents.
- Codex documentation patterns: repo instructions through AGENTS.md, local CLI execution, code review, subagents, approval modes, and controlled workflow automation.
- Scout-specific PRD requirements: LangGraph orchestration, LangSmith observability, Run Event logging, Reviewer feedback loop, Mock-first demo, evidence-backed Claims, and competition-ready traceability.
