# Scout SOP - AI Coding and Agent Execution Standard

**Version**: v2.0  
**Date**: 2026-05-28  
**Applies to**: Scout coding agents, product agents, human operators, reviewer agents, and parallel sub-agents  
**Primary context**: `PRODUCT_DEFINITION.md` -> `PRD_0528.md` -> this SOP

---

## 1. Purpose

This SOP defines how Scout should be built and operated with AI coding agents.

Scout is not a generic report generator. It is an **AI competitive analysis workbench** whose main output is a Chinese-first **竞品调研报告 / Competitive Analysis Report**, and whose system advantage is an auditable multi-agent research tree.

Every implementation decision must preserve three things:

1. The final report is useful for product, strategy, and investment-style decision making.
2. Every important intermediate artifact can be inspected as Markdown.
3. The system remains robust, traceable, and cheap enough to demo without uncontrolled reruns.

## 3. Non-Negotiable Architecture Rules

| Rule | Meaning |
|---|---|
| Product first | The demo should feel like a real competitive-analysis workbench, not a technical toy. |
| Main flow is serial | `Researcher -> Analyst -> Editor -> Reviewer`. |
| Internal work is tree-shaped | Main nodes may fan out into tracks/modules/sub-agents, then fan in to synthesis artifacts. |
| Planning is mandatory | Researcher and Analyst must plan before executing. |
| Researcher uses Plan + ReAct | It plans problem space/search tracks, then iterates through search/read/fallback/evidence extraction. |
| Markdown is primary | Human-readable Markdown artifacts are the main communication layer. |
| JSON is secondary | JSON indexes support API, frontend tree navigation, status, validation, and tests. |
| No shared parallel writes | Parallel sub-agents never write the same file. Parent/orchestrator writes synthesis and index. |
| Reviewer does not auto-burn tokens | Reviewer outputs scorecard and revision plan by default; P0 may regenerate only the Editor report from existing analysis. |
| Mock data is collection fallback only | Mock pack can replace crawling. Agent reasoning must call the real configured LLM or fail loudly. |

## 4. Standard Coding Loop

Use this loop for every non-trivial change:

```text
Explore -> Plan -> Implement -> Verify -> Review -> Commit/Hand Off
```

### 4.1 Explore

The coding agent must identify:

- Relevant Definition/PRD/SOP sections.
- Files to read.
- Files likely to change.
- Public contracts that must not break.
- Risks, unknowns, and affected demo path.

No code edits during Explore unless the task is explicitly a small documentation edit.

### 4.2 Plan

The plan must include:

- Goal.
- Write scope.
- Read-only scope.
- Acceptance criteria.
- Verification commands.
- Branch decision.
- Rollback or recovery plan.

For architecture, prompt, artifact, or API work, mention the matching PRD requirement IDs when available.

### 4.3 Implement

Implementation rules:

- Keep diffs scoped.
- Follow existing stack: Vite + React frontend, Python + FastAPI backend, LangChain + LangGraph agent runtime.
- Prefer explicit contracts over clever abstractions.
- Do not mix unrelated frontend, backend, data, docs, and dependency changes in one large task.
- Do not change public schemas/API without updating docs, tests, and frontend calls.
- Keep comments short and useful.
- Preserve all generated child artifacts unless the user explicitly requests cleanup.

### 4.4 Verify

Minimum verification by change type:

| Change type | Required verification |
|---|---|
| Backend API/model | Import check, schema validation, endpoint smoke path |
| LangGraph/agent runtime | Run a mock task, inspect run events, inspect artifact tree |
| Agent prompt | Run one task or at least one node-level prompt smoke test; inspect Markdown output |
| Frontend | Build/typecheck if available, manual workbench path, no layout break |
| Artifact/data contract | Validate index JSON and open Markdown artifact through API/frontend |
| Docs only | Search stale terms, confirm commands/ports/paths match repo |

If a command cannot run because dependencies or credentials are missing, document the exact blocked command and reason.

### 4.5 Review

Review must answer:

- Does this satisfy `PRODUCT_DEFINITION.md` and `PRD_0528.md`?
- Is the diff smaller than necessary?
- Did it introduce unnecessary dependencies?
- Did it preserve runtime logging and artifact traceability?
- Did it avoid secrets and private data?
- Does the demo path still work at frontend `5003` and backend `8000`?

### 4.6 Commit or Hand Off

Commit only after verification if the user asked for Git work. Otherwise, hand off with:

- Changed files.
- Implementation summary.
- Verification performed.
- Known risks or unfinished follow-up.

Do not treat a confident explanation as verification.

## 5. Branch and Git Policy

Git is the development log. Do not create a separate development diary unless the user asks. Runtime behavior belongs in `runtime/logs`, `runtime/runs`, and artifact Markdown.

### 5.1 Branch Naming

For AI coding agents, prefer:

```text
codex/<short-scope>
```

Examples:

```text
codex/artifact-tree
codex/editor-agent
codex/research-workbench
codex/reviewer-scorecard
```

If the team already uses `feature/*`, `fix/*`, or `docs/*`, follow the active repo convention.

### 5.2 Must Use a Branch

Open a branch for:

- Runtime code changes.
- Schema/API changes.
- LangGraph flow changes.
- Agent prompt or reviewer rubric changes.
- Frontend interaction or visual redesign.
- Data pack or artifact contract changes.
- Dependency/build changes.
- Large documentation rewrites.

### 5.3 May Direct-Push to Main

Direct `main` edits are acceptable only when all are true:

- The change is a tiny doc typo or wording clarification.
- It does not alter product scope, architecture, prompt behavior, API, schema, dependency, or demo flow.
- The diff is small enough to review at a glance.
- The user has not asked for branch-based work.

Never direct-push secrets, `.env`, generated junk, broken runtime artifacts, or broad refactors.

### 5.4 Merge Gate

Before merging:

1. Show changed files.
2. Show verification commands and results.
3. Confirm no secrets/private data.
4. If agent/runtime changed, run one end-to-end mock task.
5. If frontend changed, inspect the main demo path.
6. If reviewer changed, inspect `review_scorecard.md` and `revision_plan.md`.
7. Record latest successful `task_id`, `run_id`, branch, and commit in run summary or PR notes.

## 6. Artifact SOP

Scout uses:

```text
Structured Markdown First + Artifact Tree + JSON Index
```

### 6.1 Required Artifact Tree

```text
runtime/artifacts/{task_id}/
  researcher/
    research_plan.md
    tracks/
      market_research.md
      user_research.md
      competitor_research.md
      product_research.md
      tech_research.md
      business_research.md
      risk_research.md
    research_synthesis.md
    index.json

  analyst/
    analysis_plan.md
    modules/
      market_analysis.md
      user_analysis.md
      competitor_landscape.md
      product_feature_analysis.md
      tech_analysis.md
      business_model_analysis.md
      risk_analysis.md
    analysis_synthesis.md
    index.json

  editor/
    editorial_plan.md
    final_report.md
    editorial_notes.md
    index.json

  reviewer/
    review_scorecard.md
    revision_plan.md
    index.json
```

Not every dynamic branch must exist for every category. But `market`, `user`, and `competitor` are mandatory core branches.

### 6.2 Markdown Rules

Markdown artifacts must be:

- Chinese-first, with English terms where natural.
- Structured enough for downstream agents to parse.
- Written in conclusion-first order where applicable.
- Honest about confidence, evidence, and gaps.
- Linkable from `index.json`.

Markdown artifacts must not:

- Hide evidence gaps.
- Delete child outputs after synthesis.
- Contain API keys or private raw data.
- Present unsupported judgments as facts.

### 6.3 JSON Index Rules

Each agent-level `index.json` should include:

- `task_id`
- `agent`
- `artifact_id`
- `path`
- `title`
- `type`
- `status`
- `parent`
- `children`
- `dependencies`
- `confidence`
- `created_at`
- `updated_at`

JSON is for navigation, validation, and frontend rendering. It is not the primary narrative surface.

## 7. Runtime Logging SOP

Runtime logs are product evidence. They should show what happened, where it failed, and what artifact was produced.

### 7.1 Locations

| Log | Location |
|---|---|
| Event stream | `runtime/logs/{task_id}.jsonl` |
| Run summary | `runtime/runs/{task_id}/summary.md` |
| Agent artifacts | `runtime/artifacts/{task_id}/...` |
| Optional trace mirror | `runtime/traces/{task_id}.jsonl` or storage equivalent |

### 7.2 Required Run Metadata

Every run should record:

- `task_id`
- `run_id`
- `git_branch`
- `git_commit`
- `data_pack`
- `schema_pack`
- `llm_provider`
- `model_alias`
- `langsmith_trace_id` or local trace id
- fallback usage
- artifact refs
- reviewer verdict

### 7.3 Required Events

| Event | Required when |
|---|---|
| `TASK_CREATED` | Task is created |
| `RUN_STARTED` | Run begins |
| `NODE_STARTED` | Main agent node begins |
| `PLAN_CREATED` | Researcher/Analyst/Editor plan artifact saved |
| `SUBTASK_STARTED` | Internal track/module begins |
| `SUBTASK_SUCCEEDED` | Internal track/module succeeds |
| `SUBTASK_FAILED` | Internal track/module fails |
| `FALLBACK_USED` | Collection/source fallback is used |
| `ARTIFACT_SAVED` | Markdown or JSON artifact saved |
| `NODE_SUCCEEDED` | Main agent node succeeds |
| `NODE_FAILED` | Main agent node fails |
| `REVIEW_ISSUE` | Reviewer identifies an issue |
| `REVIEW_DECIDED` | Reviewer returns pass/revise/accept_with_limitation |
| `REPORT_REGENERATED` | Editor regenerates final report from existing analysis |
| `RUN_COMPLETED` | Run succeeds |
| `RUN_FAILED` | Run fails |

### 7.4 Redaction

Before writing logs:

- Remove API keys and `.env` values.
- Mask emails and phone numbers if present.
- Do not store raw private interview text.
- Store source excerpts only when public or authorized.

## 8. Product Agent SOP

### 8.1 Researcher

Researcher must follow:

```text
Plan -> ReAct collection loop -> Evidence extraction -> Research synthesis
```

Required outputs:

- `research_plan.md`
- `tracks/*.md`
- source/evidence records
- `research_synthesis.md`
- `index.json`

`research_plan.md` must include:

- Problem Space Map.
- Competitor discovery logic.
- Search Playbook.
- Mandatory and dynamic research tracks.
- Sub-agent assignment.
- Fallback rules.

Researcher can use mock data for collection, but the reasoning and evidence structuring still use the configured real LLM when enabled.

### 8.2 Analyst

Analyst must follow:

```text
Evidence Reality Check -> Analysis Plan -> Module analysis -> Analysis synthesis
```

Required outputs:

- `analysis_plan.md`
- `modules/*.md`
- `analysis_synthesis.md`
- `index.json`

Analyst does not search for new competitors. It writes module-level analysis articles using Researcher artifacts. Each module should include a structured Claim Pack:

```markdown
## Claim Pack
| Claim | Confidence | Evidence refs | Uncertainty | Decision meaning |
|---|---|---|---|---|
```

### 8.3 Editor

Editor 是 **主编 / Report Editor-in-Chief**，不是简单 writer。

Required outputs:

- `editorial_plan.md`
- `final_report.md`
- `editorial_notes.md`
- `index.json`

Editor must create a coherent report from Analyst modules. It can form cross-module synthesis, but every substantial judgment must be traceable to Analyst modules and evidence.

### 8.4 Reviewer

Reviewer is physically a single node in P0, but its prompt should simulate a committee:

- Evidence Reviewer
- Product Reviewer
- Strategy Reviewer
- Editorial Reviewer
- Risk Reviewer
- Originality Reviewer

Required outputs:

- `review_scorecard.md`
- `revision_plan.md`
- `index.json`

Reviewer verdicts:

- `pass`
- `revise`
- `accept_with_limitation`

Reviewer must not automatically trigger full-chain reruns. For P0, it may recommend:

```text
Regenerate Final Report from Existing Analysis
```

This means rerun Editor only.

## 9. Failure and Recovery SOP

| Failure | Behavior |
|---|---|
| LLM unavailable | Retry with bounded attempts, then fail loudly; never use fake LLM reasoning. |
| LangSmith unavailable | Continue with local trace mirror and log `FALLBACK_USED`. |
| Web/crawler unavailable | Use mock data pack if configured; mark source gap clearly. |
| One internal subtask fails | Preserve successful sibling artifacts; write failure status; synthesize with gaps if acceptable. |
| Markdown artifact validation fails | Retry formatting once; if still invalid, mark node failed. |
| Reviewer finds report-layer issue | Offer Editor regeneration from existing analysis. |
| Reviewer finds evidence/research gap | Write revision plan; do not automatically rerun full chain in P0. |
| Code regression | Prefer a fix commit; use `git revert` for committed changes when needed. |

Never run destructive Git commands unless the user explicitly asks.

## 10. Coding Sub-Agent Parallel SOP

Use coding sub-agents only when work can be split by ownership and does not require shared mutable files.

### 10.1 Good Uses

- Frontend artifact tree UI while backend API is frozen.
- Backend artifact storage while prompts are drafted separately.
- Data pack enrichment.
- Prompt drafting for one agent at a time.
- Read-only architecture review.
- QA smoke testing.

### 10.2 Bad Uses

- Multiple agents editing the same file.
- Shared schema still being debated.
- Product philosophy or report structure still unclear.
- One bug blocking the immediate local step.
- Broad refactors without a contract.

### 10.3 Sub-Agent Brief Template

```text
Goal:
Read first:
Allowed write paths:
Read-only paths:
Do not touch:
Architecture constraints:
Acceptance criteria:
Verification:
Expected final summary:
```

### 10.4 Merge Order

1. Product definition and contracts.
2. Artifact schemas and storage.
3. Backend orchestration.
4. Agent prompts.
5. Frontend workbench.
6. Data packs.
7. Tests and demo docs.

## 11. Prompt Engineering SOP

Agent prompts must be stored as standalone Markdown files under `backend/app/prompts/agents/`. Do not hard-code system prompts in Python.

Prompt requirements:

- State the agent role and boundaries.
- State required inputs.
- State required outputs and artifact paths.
- State quality rules.
- State forbidden behavior.
- State language policy: Chinese-first output, English terms allowed.
- State evidence/confidence format.
- State failure behavior.

Prompt files should align with:

- `PRODUCT_DEFINITION.md`
- `PRD_0528.md`
- This SOP

Any prompt change that modifies agent behavior requires at least one smoke run or a documented blocked verification.

## 12. Smoke Test SOP

Run this before demo review or after architecture/prompt/runtime changes:

1. Start backend on `http://127.0.0.1:8000`.
2. Start frontend on `http://127.0.0.1:5003`.
3. Create a task with `data/packs/ai_agent`.
4. Run analysis.
5. Confirm main flow: `Researcher -> Analyst -> Editor -> Reviewer`.
6. Confirm artifact tree exists.
7. Open `researcher/research_plan.md`.
8. Open at least one Research track.
9. Open `analyst/analysis_plan.md`.
10. Open at least one Analyst module.
11. Open `editor/final_report.md`.
12. Open `reviewer/review_scorecard.md` and `reviewer/revision_plan.md`.
13. Confirm JSONL run events exist.
14. Confirm no `.env`, keys, private raw data, or junk artifacts are staged.
15. If Reviewer returns `revise`, confirm it produces a precise revision plan and does not automatically rerun the full chain.
16. If report-layer regeneration is triggered, confirm only Editor is rerun from existing analysis.

Record the latest successful `task_id` in the final handoff or PR note.

## 13. Stop and Ask Rules

Stop and ask before:

- Changing core product positioning.
- Changing final report structure.
- Changing artifact tree contract.
- Adding full automatic rerun behavior.
- Removing logging, tracing, reviewer, or artifact visibility.
- Adding a major dependency.
- Touching `.env` or secret-bearing files.
- Editing files assigned to another active agent.
- Using destructive Git commands.

## 15. Source Basis

This SOP adapts common AI coding best practices:

- Keep tasks small and context-rich.
- Use version control as the development audit trail.
- Prefer hard verification over verbal confidence.
- Split parallel agent work by ownership.
- Store durable project rules in repo documents.
- Treat logs, traces, artifacts, and review outputs as product surfaces, not hidden debug residue.
